### Added

- **Session-scoped shell-prefix grants (the `[p]` mechanism above) now have their own review and revoke surface** — board item `01M350FR4SM6QT0EM6M35EY5AZ`. Until now that grant class had no way to see what had been authorized this session, or take it back — the exact class most easily forgotten, since the whole point of granting one is that it stops asking. `PermissionBroker::active_shell_prefix_grants`/`revoke_shell_prefix_grant`/`revoke_all_shell_prefix_grants` (facade: `Conway::active_shell_prefix_grants`/`revoke_shell_prefix_grant`/`revoke_all_shell_prefix_grants`, the latter two taking only `conway_core` types at the boundary, matching every other permission facade method) add the missing surface, kept structurally separate from the durable pattern-grant review/revoke methods (`active_patterns`/`revoke_pattern`, `active_structured_allow_rules`/`revoke_pattern_rule`) for the same reason the grant store itself is separate: this class has no `PatternRule`/`Rule` identity, no `PatternOrigin`, and nothing to persist. `/settings` → permissions → "shell prefixes" lists every grant exactly as granted, with its scope; `Enter` on a row revokes just that one, a "revoke all shell-prefix grants" row clears every one, and a revoked grant cannot resurrect (there is no cache path that could re-authorize it — the next matching command prompts again). **Deliberately does NOT get a status-line indicator** the way `AUTO-ALLOW`/`plan` do — see `view/status.rs::mode_ladder`'s own doc for the "narrowest, shortest-lived grant class, not the loudest" reasoning: this class is strictly narrower than the durable pattern grants beside it (no persistence, one non-compound command, operator-edited and operator-visible), and those already get no status-line rung either. See `docs/permissions.md`'s "The shell-prefix grant" section and `docs/interactive.md`'s matching section for the operator-facing account.

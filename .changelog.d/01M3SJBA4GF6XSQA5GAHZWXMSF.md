### Fixed

- **A plugin command issued after `/model`/`/role` no longer answers for the wrong session** — board item `01M3SJBA4GF6XSQA5GAHZWXMSF`. `/conway.checkpoint.list`, `/conway.history.*`, and every other implicit-session plugin command now resolve `CommandCtx::session_id` against the session of the agent the operator is actually focused on (`AppState::focused_agent`), not the TUI's original root session. Before this, a `/model`/`/role` switch moved focus to a forked child with its own session, and every implicit-session command kept answering for the pre-switch session instead — so a fresh edit was invisible to `/conway.checkpoint.list` ("no snapshots recorded yet"), and rolling back could not find what it was looking for. `conway_cli::tui::commands::Host::session_for` is the one resolver every such command now goes through.
- **`--session <id>` now also accepts an agent id**, resolved to the session it owns. The TUI's own `/model`/`/role` switch notice — the one place an operator is actually invited to copy an id from — prints an agent id, never a session id (the two are different ids even for an unforked root agent); pasting it into `conway conway.checkpoint.list --session <that-id>` used to fail with "unknown session". `docs/plugins/checkpoint.md` documents the fallback and why the TUI's own agent-id vocabulary was kept rather than widened to print session ids too.

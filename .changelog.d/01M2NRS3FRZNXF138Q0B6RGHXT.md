### Fixed

- **`conway routes explain` no longer prints `unknown` for a candidate's window on a default install** — board item `01M2NRS3FRZNXF138Q0B6RGHXT`. `conway.routing` (the capability-filtered `DeclarativeRouter`) is not one of guided setup's default-installed plugin ids, so an ordinary install runs on `conway_core::routing::MinimalRouter`, which holds no capability index at all — every `ExplainEntry` it produced carried `capabilities: None`/`context_window_source: None` unconditionally, rendered `unknown` even when `.conway/models.json` declared a real window for the exact candidate being explained. `Conway::explain_routing` now overlays its own already-resolved `CapabilityIndex` (`ConwayBuilder::build`'s step 5 — the SAME index a compiled-in router filters admission against, populated regardless of which router is selected) onto any entry a producing `RoutingExplainer` left with no window/provenance; `conway routes explain` additionally falls back to the same dialect-default-floor computation the first-turn floor notice already uses for a model reachable only through a role's chain and never declared in `models.json` at all, so the assumed-floor case (`floor (assumed)`) resolves too. `token_fidelity`/`cache_reporting` are deliberately unchanged — both stay `unknown` under `MinimalRouter`, exactly as before.

### Changed

- **Ruling recorded: `conway.routing` stays out of the default plugin opinion set.** The window/provenance fix above answers the observable defect without installing a capability-/health-filtering router by default — a materially larger, unrelated behavior change to real turn routing this item did not ask for. `first_party_plugins::DEFAULT_OPINION_SET` is unchanged.

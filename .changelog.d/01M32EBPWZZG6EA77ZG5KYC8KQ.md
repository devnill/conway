### Added

- **The permission prompt's `[p]` key now offers a session-scoped shell-command PREFIX grant for `bash`/every other `ShellCommand` tool** — board item `01M32EBPWZZG6EA77ZG5KYC8KQ`, a live-reproduced finding: driving one real feature through conway issued roughly 70 individual permission prompts, nearly all shell commands differing only in their arguments, because the only "allow always" available for a shell tool keys on the EXACT command string and the durable prefix-pattern grant is refused outright for one by design (board `01KZDDPC5MMD49F6JPV9CW4TVM` — that refusal is unchanged and unrelated to this item). `[p]` on a `ShellCommand` prompt now opens a free-text editor seeded with a narrow, two-token default (`conway_core::permission_pattern::default_shell_prefix` — e.g. `git status` from `git status --short`, never the bare `git`), which the operator can widen or narrow before accepting at the prompt's existing `Session`/`Agent`/`AgentSubtree` scope (`Ctrl-S` cycles it while the editor is open, since the prefix text can itself legitimately contain the letter `s`). The grant lives ONLY in `PermissionBroker`'s own new in-memory store (`remember_shell_prefix_grant`/`shell_prefix_grant_allows`), checked between the exact-args cache and the durable pattern-allow step, reusing `GrantScope`/`grant_scope_for` verbatim so scope semantics cannot drift from the cache's or the durable patterns' own — it is never written to `permissions.json` at any scope, is gone after a fresh broker (a restart), and is recorded under a new `PermissionDecisionRecordKind::ShellPrefixGrant` so it can never be mistaken for the durable `Pattern` mechanism in the session's own transcript. A `Structured` tool is unaffected — it keeps the pre-existing `[p]` field editor exactly as it was. See `docs/interactive.md`'s "The permission prompt" section for the operator-facing walkthrough and `docs/permissions.md`'s Limits section, which still states, unchanged, that a durable pattern grant can never cover a shell command. **Compound-command exclusion, required before this could ship (caught in review):** `prefix_matches` alone returns `true` the instant a grant's own tokens are exhausted, so an unguarded `git status` grant would have silently extended to `git status && rm -rf /`, `git status | sh`, `git status $(rm -rf /)`, and anything else sharing that start — the exact defect the durable prefix-pattern mechanism was permanently closed for. `conway_core::permission_pattern::shell_command_is_compound` is now checked against both the candidate call and the proposed grant's own prefix: a candidate that chains (`&&`/`||`/`;`/newline), pipes (`|`), backgrounds (`&`), or substitutes another command (`$(...)`/backticks/`<(...)`/`>(...)`) is never covered by any shell-prefix grant and prompts normally, and a prefix containing one of those constructs is refused at creation with the reason shown in the editor. This is a scope limit, not a text-scanning safety net — an ordinary redirect or variable expansion is unaffected.

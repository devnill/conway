### Added

- **`conway.toolindex`: deferred tool schemas** — board item `01M1YS138H8T0HNV5YMZ6KD767` part 1. A new opt-in first-party plugin (`crates/conway-plugin-toolindex`) narrows every non-built-in tool's announced JSON schema down to a one-line `name: description (call describe_tool(name="...") for the full schema)` index entry, plus a `describe_tool` tool that returns the full description and schema on demand and keeps that tool fully announced for the rest of the session. Built-in `conway.fs`/`conway.shell`/`conway.subagent`/`conway.report` tools stay fully announced always; a real session measured the `tool registry` `/context` entry at ~10,087 estimated tokens with one MCP server installed, versus ~4.4k with only built-ins — this plugin exists to shrink that gap. `"plugins": { "install": ["conway.toolindex"] } }` opts in; not part of the default first-run opinion set (a deferred tool's first call may cost one extra `describe_tool` round trip, a trade-off that ruling never evaluated). See `docs/plugins/toolindex.md`.
- **`roles.<alias>.tools = { include: [...], exclude: [...] }` config surface, now wired live** — board item `01M1YS138H8T0HNV5YMZ6KD767` part 2. `settings.json` parses a `deny_unknown_fields`-strict `[roles.<alias>.tools]` table (glob include/exclude lists, mirroring the `AgentDef`/`SessionSpec` tool-selector vocabulary already used elsewhere); `RoleToolsConfig::resolve` turns it into a concrete `ToolSelector` against the real installed-plugin tool universe once, at `ConwayBuilder::build` time, and `Runtime::set_role_tools` hands the resolved per-role table to `conway-runtime`. A root (`start_root`/`resume_root`) and a forked/spawned child routed through a narrowing role (`SubagentHost::start`) both AND that selector into whatever the call's own `agent_def`/`tools` override already narrows them to (`runtime::root::narrow_tools_for_role`) — a role naming no `tools` table changes nothing, exactly as before. See `docs/routing.md`'s new "Narrowing a role's own tool set" section.
- **`/context`'s tool-registry entry breaks down by plugin** — board item `01M1YS138H8T0HNV5YMZ6KD767` part 2 (continued). The single `tool registry — N tok` line now gets one indented line per declaring plugin beneath it (tool count + an independent per-plugin token estimate), so an operator can see who inside that combined figure actually costs what. Reads two new thin registry surfaces (`PluginRegistry::tool_plugin_ids`, threaded through `Runtime`/`Conway` the same way `Conway::tool_specs` already is) and estimates each plugin's own slice with the same heuristic-chars4 formula the combined segment already uses — an approximation like every other `/context` figure, not a claim of exact wire-byte parity, and one that can drift from the parent row's own total for a role-narrowed agent (the breakdown is whole-process, not narrowed to one agent's own view — no existing surface exposes that narrower view for the CLI to read instead).

### Changed

- **`docs/plugins/README.md`** gains a `toolindex.md` index row and bullet, and its shipped-first-party-plugin count moves from fourteen to fifteen (and its three stale "twelve" mentions, already wrong before this change, are corrected to match).
- **`docs/agents.md`**'s `/context` section now notes that the `tool registry` entry's `tokens_est` includes every installed MCP server/subprocess plugin, and that `conway.toolindex` is what narrows it.

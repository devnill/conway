### Fixed

- **Closing the TUI's terminal, or a process manager stopping it with `SIGTERM`, no longer leaves it running unsupervised.** Before this, `SIGTERM`/`SIGHUP` killed the TUI process before any destructor ran: an in-flight `!` command's child process (and anything it had spawned) was orphaned, not killed, and the terminal was never restored. The TUI now installs the same `SIGTERM`/`SIGHUP` watcher one-shot mode already uses and reacts to the first delivery of either through the exact same shutdown `/quit`/`Ctrl-D`/double-`Ctrl-C` already run — including killing an in-flight `!` command's whole process group, bound-awaited, not fire-and-forget — then restores the terminal and exits with the same documented signal-specific code one-shot mode already uses (143 for `SIGTERM`, 129 for `SIGHUP`). A second signal while that cleanup is still running still forces an immediate exit, mirroring one-shot mode's own safety valve, deliberately without restoring the terminal first — see `crates/conway-cli/src/tui/mod.rs`'s `install_panic_hook` doc for why the same tradeoff already applies to a panic, which this item leaves unchanged (it still restores the terminal on its own, but does not attempt to kill a tracked child's process group).
- **Quitting the TUI (`/quit`, `Ctrl-D`, double-`Ctrl-C`, or the SIGTERM/SIGHUP path above) now also stops a model-issued tool call that is still running — a `bash` call in particular — without ending the session itself.** Previously, nothing on any quit path ever interrupted the root session's own in-flight turn, so a `bash` tool call's whole process group (never `kill_on_drop`'d, unlike an MCP server or plugin subprocess) was simply abandoned when the TUI process exited — not even its own leader was killed, since dropping an un-`kill_on_drop`'d child sends it no signal at all. Every quit path now aborts the in-flight turn on the root and on any other subagent the TUI knows about — the same non-terminal abort a single `Ctrl-C` press already uses, never a terminal cancel — so a held tool's process group is actually killed, bound-awaited, before the process exits, while the session itself stays exactly as resumable afterward (`--resume`/`/resume`) as it always was.
- **A quit landing right after a model-issued fork/spawn can no longer miss that brand-new subagent's own in-flight tool call.** The "every quit path aborts every known subagent" fix above walked only the TUI's own event-sourced view of the agent tree, which can briefly lag a `conway_fork`/`conway_spawn` the runtime has already started but whose spawn event this process has not finished applying yet — a quit landing in that narrow window left the new subagent's own held tool running, unkilled, same as before either fix. Quitting now also reads the runtime's own authoritative, lag-free agent tree (filtered to this session) and aborts anything found there too, so a spawn the runtime already knows about is always covered, even one this process's own view has not caught up to yet.

### Changed

- **`docs/scripting.md`'s exit-code table** now says outright that its 129/143 "terminal status is `Cancelled`" wording describes one-shot (`-p`) mode only: the TUI exits with the identical codes for the identical signals, but (as the fix above already does) aborts the current turn non-terminally instead, leaving the session resumable with nothing terminal published. `docs/interactive.md`'s own link into that table now says the same — code only, not the terminal-status wording — so the two pages no longer read as contradicting each other.

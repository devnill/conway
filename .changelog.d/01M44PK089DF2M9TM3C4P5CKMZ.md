### Changed

- **`tui.busy_input` now defaults to `steer`, not `queue`.** A message typed while the agent was busy under `queue` was indistinguishable, on screen, from one that had simply been lost until it was actually sent; `steer` delivers it at the running turn's own next step instead. A steer that lands once the agent has ALREADY finished its turn and is idling — the operator's own next message never having arrived yet — now starts a fresh turn of its own automatically, carrying that text, rather than sitting durable-but-unread until some later, unrelated prompt happens to pick it up.
- **`!>cmd` no longer spends a model turn just to add its own output to context.** The command's output is still durable and context-admitted the instant it finishes, exactly as before, but the agent only actually reads and answers it the next time a real turn runs — the operator's own next message or steer — never as an automatic side effect of running the command.
- **A permission prompt's `[a]` ("allow always") now requires a deliberate second keystroke.** The first press only arms a confirmation (the prompt's own hint line says so); the same key again, or `Enter`, commits the grant, and `Esc` backs out with no decision made. No single stray keystroke can grant broader than "allow once" anymore.
- Steered messages are labelled `steer>` in the transcript and the input title's queued-strip count, distinct from a still-withheld `queued>` message — the two differ in exactly the fact an operator asking "did that already reach the model?" cares about.
- The input title keeps showing the queued/steer count while a permission prompt is on screen (`"input (paused) — 1 queued: ..."`), instead of hiding it behind the bare word "paused".
- F2 ("send now") and `busy_input = interrupt`'s own abort notice now says what actually happened ("sent now — the reply in progress was stopped") instead of the generic "turn aborted (...); type to continue", which was wrong in both cases: the message had already been resent by the time the notice appeared.
- The bare `exit`/`quit`/`q`/`:q`/`:wq` guard's hint ("press Enter again to send the word to the model") is now true — the word is restored to the input box instead of the box staying empty.

### Fixed

- **Typed input could answer a permission prompt it interrupted mid-sentence.** A key arriving within about a second of the prompt appearing, or while the input box already held a draft at that instant, now lands in the draft instead of being evaluated as a decision — closing the exact shape a dogfood session hit (`a`, mid-typed as part of "also tell me...", answering "always" for the rest of the session).
- **A bare `!` command's multi-line output rendered as a single line with `�` standing in for every lost line break.** The render boundary's own control-character sanitizer was applied to the whole multi-line block before splitting it into lines, so every real newline was replaced by the same placeholder used for a stray control character — splitting on the raw text first, then sanitizing each resulting line, fixes both `!` and `!>` alike.
- **A steer delivered to an agent that had already idled in the exact same scheduling pass as the gate closing could leave a stray wake behind**, which would later resume a wholly unrelated idle period with nothing actually pending (a silent, spurious turn). The resume wait now re-checks, on every wake, that a steer genuinely landed or a prompt's own record is newer than the moment the gate was armed — a bare wake with nothing behind it goes back to sleep instead of proceeding.
- **The permission-prompt typeahead guard bypassed the `vim` editing engine.** With `tui.editor_mode = "vim"` in NORMAL mode, a key like `d`/`x`/`i`/`l`/`h`/`w` arriving inside the typeahead window used to be inserted as a literal character instead of running as the vim command it is, and left any pending operator stale. It now routes through the same vim-aware draft seam ordinary typing uses.
- **A bracketed paste vanished entirely if it arrived while a permission prompt was showing.** It now lands in the draft, exactly like typed-through text, and never answers the prompt either way.

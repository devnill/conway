### Fixed

- **`/diff` and `conway sessions show --diff` no longer report "no files edited or written yet in this session" after real, applied edits** — board item `01M2V6HMBAWKM0GG90J14K4Q8F`. Both surfaces took each path's CURRENT on-disk bytes as the diff baseline, read at the moment the command runs. By then the recorded `edit`/`write` calls have already landed, so the baseline *was* the result: re-applying the calls on top changed nothing (an `edit` whose `old_string` is gone is refused; a `write` rewrites what is already there), every diff came out empty, and the command announced that nothing had been touched. `/diff` now diffs against the bytes each path held when the session first proposed a call against it, captured before that call ran, and `sessions show --diff` — which replays a log that persists no file snapshots — reconstructs the same baseline by un-applying the recorded calls from the file's current bytes. Concurrent edits conway did not make land on both sides of the reconstruction and are correctly left out of the output.

### Changed

- **The cumulative-diff engine (`conway-cli`'s `diff::cumulative_diffs`) now takes the baselines it should use rather than reading them from disk itself.** The interactive TUI passes the snapshots it captured at tool-propose time, so `/diff` is exact and performs no disk access at all; the headless reader passes an empty map and falls back to reconstruction. The one case the two can still differ is a `write` that clobbered pre-existing content: the live session knows what was displaced, a replayed log genuinely does not, and `sessions show --diff` reports such a file as wholly added. Both behaviours are now stated in the functions' own docs, which previously asserted the opposite.

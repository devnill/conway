### Changed

- **An untrusted project `.conway/` no longer stops conway from starting** — board item `01M3TJQGJHFFPWE2YYN60WN1XB`, superseding board item `01M2M5EM73GA15NMQ1H87TTEDP`'s "refuse outright" ruling for a project `settings.json`. Its file(s) are IGNORED — never applied, never silently skipped — and conway starts anyway. Ignoring is never silent: a transcript notice at session start names the exact file and the command that applies it, a persistent `project config ignored` status-line marker stays visible for the rest of the session (forced in regardless of `[tui.status_line]` configuration, and rendered in a fixed style no `[tui.theme]` — trusted or not — can hide), and a non-interactive run (`conway -p`, `sessions`, `routes`, …) prints the same notice to stderr. An untrusted project's `[tui]` section (theme, status-line fields, …) is itself ignored too, the same way every other key is. Editing a trusted file re-arms the notice, with wording that distinguishes "never trusted" from "trusted, then edited."
- **One trust act now covers a project's `settings.json` AND `permissions.json`.** `conway trust project` (headless) reviews and records consent for both files, printing each one's contents, in a single invocation. The TUI's `/trust permissions` now shows BOTH files in the same preview card (a second, clearly labelled section for `settings.json` when the project has one) and records consent for exactly the bytes shown — never a fresh re-read — before confirming either. `conway trust settings` is kept as an alias of `project`. Each file still gets its own independent trust record; editing either one re-arms only that one.
- **A remembered permission grant (`[a]`/`[p]` at the prompt) is now persisted in the operator's own user-scope config directory, keyed to the project, instead of being appended to the project's `.conway/permissions.json`.** A prompt answer never becomes a byte in the checkout — no `git diff` surfaces it, no `git pull` can pick up someone else's. This file is always trusted by authorship, so a remembered grant there needs no further `/trust` step to apply at the next launch. Existing grants already recorded in a project's own `permissions.json` from before this item are left alone and keep working once the project is trusted.

### Removed

- **BREAKING: `FacadeError::UntrustedProjectSettings` is removed.** `ConwayBuilder::discover` no longer fails outright for an untrusted project `settings.json` (see above) — `config::merge::load_trust_gated` skips that one layer and reports a `ConfigWarning` instead, and the hard-refusal error variant this produced has no replacement. A caller matching on this variant will fail to compile; match on `ConfigWarning { code: WarningCode::UntrustedProjectConfigIgnored, .. }` in `Conway::warnings()` instead. Plain `conway::config::load`/`load_ignoring_user_config`/`merged_document` are unaffected by the new trust gate at all: it lives in the new, `pub` `config::merge::load_trust_gated`/`merged_document_trust_gated` (also used by `conway-cli`'s own "what would actually load" checks), not in the merge mechanism's unconditional entry points.

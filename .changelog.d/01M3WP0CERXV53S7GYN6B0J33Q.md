### Fixed

- **SECURITY: confirming `/trust permissions` now trusts and installs exactly the bytes the preview card showed, never a fresh re-read of the file.** Board item `01M3WP0CERXV53S7GYN6B0J33Q`, closing a gap a security re-review of the trust rework (commit `40aaa09a`) found: the Confirm arm called `Host::trust_permission_file` with only the path, which re-read `permissions.json` from disk both to record the trust decision and to install its `allow` rules — so a file rewritten between the preview opening and the operator's `y` (a concurrent `git pull`, a build script) silently had the NEW, unreviewed bytes trusted and granted, not the ones the operator actually looked at. `permissions.json` now has the same bytes-shown-is-bytes-trusted contract `settings.json` already got from this item's predecessor (`01M3TJQGJHFFPWE2YYN60WN1XB`): a new `Conway::trust_permission_file_bytes`/`Host::trust_permission_file_bytes`, backed by `TrustStore::trust_bytes`, takes the preview card's own `contents` and never touches the path again. Impact was bounded — `deny`/`prompt` rules always apply regardless of trust — but an `allow` rule could previously be consented to unseen. `Conway::trust_permission_file`/`Host::trust_permission_file` (path-based) are unchanged and kept for any caller that has not already read the file itself; none remain in this tree today. `conway trust project`/`conway trust settings` (the headless CLI path) already read once and passed those same bytes to both halves — verified, not changed.

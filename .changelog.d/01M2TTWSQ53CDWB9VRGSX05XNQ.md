### Added

- **`conway trust settings|list|revoke`** — board item `01M2TTWSQ53CDWB9VRGSX05XNQ`. The headless half of consent for a project-scoped `.conway/settings.json`, the same shape `conway plugin list|install|remove` already sets for `/plugin`: `conway trust settings [--path <p>]` prints the file's contents and records a decision about exactly those bytes, `conway trust list` shows every decision `trust.json` holds and whether each file still matches what was trusted, and `conway trust revoke <path>` withdraws one. Uniquely among the built-in subcommands it is dispatched before the config is built, because building the config is exactly what an untrusted project `settings.json` refuses — a command that granted consent but needed consent to run could never be reached.

### Fixed

- **An untrusted project `settings.json` no longer locks an operator out of conway with advice they cannot act on** — board item `01M2TTWSQ53CDWB9VRGSX05XNQ`. The refusal named the TUI's `/trust settings` command (the TUI is what had just refused to start, and that command did not exist — the TUI parses `/trust permissions`) and the `TrustStore::trust_settings` Rust API. Both were unreachable from the shell where conway stopped starting, and the only remedy that actually worked — deleting the file — went unmentioned. The message now names `conway trust settings --path <file>`, removing the file, and `conway trust list`/`conway trust revoke`, all of them typeable at the prompt the operator is already standing at. The guard itself is unchanged: a project file can still redirect a backend's `base_url`/`api_key`, so it is still a hard refusal, still never auto-trusted, still scoped to one path's exact bytes, and there is deliberately no blanket flag a script could set.

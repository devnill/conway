### Fixed

- **`conway --session <id> <plugin-id>.<command>` now targets the session it names** — board item `01M2TWC242P96Z3JDXWC9F3R5E`. clap accepts the root `--session` flag before any subcommand word, so that spelling always parsed — and then did nothing: the value never reached the plugin dispatch, which minted a fresh empty session and reported on *that* one while the operator was looking at the id they had just typed. Two spellings existed at the shell and only the post-subcommand one worked, which is the same defect `--session` was added to end, one spelling over. The root flag now forwards to the same resolution the post-subcommand one uses — resolved by id or name, and never creating. Giving both at once is a usage error quoting both values rather than a silent precedence rule, because guessing between two equal spellings is not safe on a surface that reaches `conway.checkpoint.rollback`.

### Added

- **End-to-end CLI coverage for the post-kill surfaces** — board item `01M2TWC242P96Z3JDXWC9F3R5E`. `crates/conway-cli/tests/postkill_session_targeting.rs` drives the real compiled binary and the real `conway-plugin-checkpoint` crate through the whole operator path: a one-shot turn calls the real `write` tool, and a *later, separate process* then asks `conway sessions show <id> --diff` what that session did (getting the path and its content back, with no `git` in the pipeline) and `conway conway.checkpoint.list --session <id>` for that one session's snapshots — contrasted against the untargeted invocation, which names the session conway minted to answer with. Both surfaces were unit-tested and neither had ever been executed.

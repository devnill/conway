### Fixed

- **A project-scoped `settings.json` reached by the ancestor walk now requires the same trust decision `permissions.json` already requires, and is refused — never silently applied or silently skipped — until you trust it** — board item `01M2M5EM73GA15NMQ1H87TTEDP`. `settings.json` can set `backends.<id>.base_url`/`api_key`, redirecting your traffic and credentials to an endpoint a cloned repository chose, not merely widening what an agent may call — strictly more dangerous than `permissions.json`'s own `allow` rules, so this gate is stricter: an untrusted project `settings.json` refuses the whole session rather than degrading quietly. `conway::config::trust::TrustStore` gains a second, independent kind (`settings_files`, the same `(absolute path, content digest)` subject `permission_files` already uses) and `guard_untrusted_project_settings`, the gate itself; `ConwayBuilder::discover()` — the no-`--config` production path — is the one call site, and `FacadeError::UntrustedProjectSettings` is the named refusal it raises. Your own user-scope `settings.json` and `--config <path>` are unaffected, exactly as `permissions.json`'s own trust already carves out.
- **`HOME` overridden for isolation (a test fixture, a `docker run -e HOME=...`, a shell session with `HOME` exported for one command) no longer lets your real, un-overridden `~/.conway/settings.json` leak back in as a *project* layer** for a working directory that still sits beneath your real home. `conway::config::discovery::project_discovery_exclusions` gains a third exclusion entry, resolved from the operating system's own account database (`getpwuid_r` on Unix) rather than the `HOME` environment variable — immune to exactly the override that used to defeat the other two entries.

### Changed

- **`docs/getting-started.md`, `docs/permissions.md`** document the project `settings.json` trust gate and the `HOME`-independent exclusion fix.

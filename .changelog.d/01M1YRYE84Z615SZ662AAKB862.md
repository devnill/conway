### Added

- **`conway_fork`/`conway_spawn` gain an optional `role` argument, and `/spawn`/`/fork` gain `--role <alias>`/`--model <backend/model>` (mutually exclusive)** — board item `01M1YRYE84Z615SZ662AAKB862`. A model choosing a role for its own child now genuinely routes the child through that role's configured fallback chain — before this, `role` was carried on `AgentKnobs` but an unconfigured alias only failed lazily, deep inside the child's own first turn, after a session had already been paid for. Naming a role this call's own `RoutingConfig` does not define is now rejected before any child session is created, as a typed `RuntimeError::InvalidSpec`/`ToolError::InvalidArguments` naming the unconfigured alias. The operator's `/spawn`/`/fork` (TUI) get both `--role <alias>` (the same routing-role vocabulary) and `--model <backend/model>` (a raw pin, an operator-only capability with no model-invoked equivalent) — the parity rule that anything a model can do to the session's own agents, the operator can do too, from one typed command, and more. Neither flag disturbs an ordinary bare `/spawn`/`/fork`, an explicit `@<agent>`/`@<agent_def>` target, or one-shot's pre-existing `--role-override`/`--model`, all unchanged.
- **The unconfigured-role rejection now lists the roles that ARE configured.** `Router` gains a `known_roles` method (defaulted to empty, so every existing implementor keeps compiling unchanged; `MinimalRouter` and `DeclarativeRouter` — the two implementors that actually hold a role table — override it), and the eager `role '<alias>' is not a configured routing role alias` refusal now appends `(configured roles: <sorted list>)`, or `(no roles are configured)` when the router genuinely has none. A caller (model or operator) who names a typo'd or nonexistent alias is told the real options, not just that its guess was wrong.
- **The `/agents` panel (and `/tree`) show the operator's own `--role`/`--model` flag.** A child created via `/spawn --role <alias>`/`/fork --role <alias>` shows `role: <alias>` on its row; one created with `--model <backend/model>` shows `model: <backend/model>` instead — right alongside the existing fork/spawn recipe label. Recorded only at the TUI command call site that actually saw the flag (mirroring the existing `switch_lineage`/`budget_warned_agents` side-table pattern, not a new `TreeNode` field), so a child a model created via its own `conway_spawn`/`conway_fork` tool call shows no such marker — the runtime's `Event::AgentSpawned` carries no role/model field for this session to have observed one from.

### Changed

- **`docs/agents.md`, `docs/interactive.md`, `docs/scripting.md`** document the model-invoked tools' `role` argument and its unconfigured-alias rejection (now naming the configured roles), the operator's `--role`/`--model` flags on `/spawn`/`/fork` and how they render on the `/agents` panel, and the `--agent`/`--model` one-shot delegation recipe (`conway -p … --agent <name> --model <backend/model>`) for the case a target backend is not yet reachable through any configured role.

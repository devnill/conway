### Added

- **An opt-in vim editing mode for the interactive TUI's input box.** `tui.editor_mode = "vim"` in `settings.json` (default stays `"emacs"`, today's readline-shaped keys unchanged), or toggled for the session from `/settings` → "display", layers modal INSERT/NORMAL/Visual editing onto the SAME input widget: `i a I A o O` to enter INSERT, `Esc` back to NORMAL; motions `h j k l w b e 0 $ ^ gg G f F t T` with counts; operators `d c y` composed with any motion, plus `dd cc yy D C`; `x X p P` (the one unnamed register); `u`/`Ctrl-R` undo/redo; `.` to repeat the last change; Visual `v`/`V` with `d y c`; `/pattern` to search within the input. The input box's border title always names the current submode. Every existing Ctrl-bound action (`Ctrl-A`/`Ctrl-E`/`Ctrl-U`/`Ctrl-K`, `Ctrl-P`/`Ctrl-N` history, `Ctrl-O`, `Ctrl-G`, `Tab`, `F2`) keeps working unchanged in both vim submodes — this is a modal layer on top of the input box, never a second, competing keymap — and `Esc` in INSERT never submits and never interrupts a running turn (`Ctrl-C` remains the only interrupt key). `docs/interactive.md`'s new "Vim editing mode" section states the exact supported subset and what is deliberately not built (no `:` command line, no named registers or macros, no text objects beyond `iw aw i" a" i( a("`). Any count is capped at 9999, so an implausibly large one (a typo, or a stray paste) can never allocate or loop far beyond what the input box could show; `cw` follows vim's own rule of changing through the end of the current word rather than consuming the whitespace after it.

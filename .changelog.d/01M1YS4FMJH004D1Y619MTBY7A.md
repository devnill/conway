### Added

- **`conway --resume`/`--fork-from` now open the interactive TUI too, and a new `conway --continue`/`-c` resumes the most recently active session with no id to type** — board item `01M1YS4FMJH004D1Y619MTBY7A`. Previously the TUI refused all three startup continuity flags outright (a usage error), and `/resume <id>` (once already running) reset to an EMPTY transcript with the code's own comment naming why: no `LogRecord` → transcript `Entry` mapping existed anywhere in this crate. Both gaps are closed together: a new `backfill_entries` mapping (`conway-cli`'s own — `conway::SessionHandle`'s `record_to_event` was read first and found to drop a replayed `Assistant` record's tool calls entirely, wrong for this purpose; `conway sessions show`'s own rendering is a bare `Debug` dump with nothing to reuse) turns a session's persisted records into transcript entries — user turns, assistant text, tool calls folded with their results exactly as they render live, child results, and a named, visible placeholder (never a silent drop) for any record kind without a dedicated line yet. `App::resolve_handle` (`tui::app::startup`) now attempts `--resume <id|name>`/`--fork-from <id|name>[@seq]`/`--continue` at startup, backfilling the transcript before any startup notice is shown; `/resume <id|name>` does the same once the TUI is already running, now accepting an operator-chosen name exactly as `--resume` does, and naming `conway sessions list` when a name or id resolves to nothing. `--continue` ranks candidate sessions by their own log file's last-write time, not by when each was first created, so an older session chatted in five minutes ago outranks a brand-new, still-empty one. `--session` did not graduate alongside the other three and stays one-shot-only. `docs/sessions.md`'s `/resume`-equals-`--resume` equivalence claim is now literally true.

### Fixed

- **The TUI's cache-status wording no longer collapses "this backend cannot report caching, ever" and "this backend can report caching but stayed quiet this turn" into the same text** — board item `01M2NS0996E139VN5R8W4PGD8V`. The turn-end summary and status line's `tokens` field previously rendered `cache: not reported[ by <backend>]` for both facts alike, so a structurally cache-incapable backend (e.g. Ollama's native `/api/chat`, which carries no cache field in its wire format at all) looked identical to a declared cache-capable backend (e.g. any `dialect: "openai"` profile) that simply had a quiet turn — the former is permanent and not actionable, the latter is exactly the signal an operator watching this line is looking for. `usage_format::cache_suffix` now also takes the focused backend's declared `CacheReporting` (already resolved once at startup via `Conway::capability_index()`, never re-derived) and renders three distinct wordings: `cache: not reported[ by <backend>]` (capable, quiet this turn), `cache: not supported[ by <backend>]` (structurally incapable), and `cache: reporting unknown[ for <backend>]` (the capability itself is unknown to this state) — mirroring `conway routes explain`'s own "a candidate this report could not ask is not the same fact as one that answered 'no'" distinction, without changing that command's own wording.
